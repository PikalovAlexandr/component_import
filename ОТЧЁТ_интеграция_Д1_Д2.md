## Отклонения от комплекта (правки под v2.13.1)

Комплект написан против Part-DB **v1.17.x**; стенд — **v2.13.1**. Потребовались 4 точечные правки:

| # | Файл | Проблема | Фикс |
|---|------|----------|------|
| 1 | `OffersBulkController:83` | `$part->addOrderdetail($od)` — метод не public в v2.13 | Заменён на `$od->setPart($part)` |
| 2 | `OffersBulkController:116-117` | `setPriceRelatedQuantity(1)` (int) и `setMinDiscountQuantity($qtyFrom)` (int) при `strict_types=1` | Приведено к `1.0` и `(float) $qtyFrom` |
| 3 | `Migration:27-29` | `getDatabasePlatform()->getName()` удалён в Doctrine DBAL 4.x | Проверка оставлена только через `::class, 'PostgreSQL'` |
| 4 | `Migration:72` | Колонка в v2.13: `orderdetails.part_id` (не `id_part`) | SQL в миграции: `od.id_part` → `od.part_id` |

### Дополнительно (несоответствие комплекта, а не кода)

- **composer dump-autoload**: после hot-копирования 5 новых PHP-файлов в `src/{Controller,State,Entity}/ComponentExt/` classmap не обновился → FileLoader Symfony падал «Expected to find class». Исправлено `composer dump-autoload`.
- **Локаль в URL**: маршруты `PartStatusController` и `OffersBulkController` регистрируются с `/{_locale}/api/...` (стандарт для Part-DB). Вызовы без `/ru/` → 404. Клиент должен слать на `/ru/api/...`.
- **serializer-naming**: у `ValidationPassport` свойство `$reportHash` маппится на JSON-ключ `reportHash` (camelCase по умолчанию), комплект же шлёт `report_hash`. Поле `errors_count` маппится корректно (snake_case = `errors_count` в JSON; нужно `$errorsCount` или добавить `#[SerializedName('errors_count')]`). Для шлюза выпуска это **не блокирует** (gate проверяет только `errors_count`), но hash паспорта остаётся пустым.

## Что НЕ проверено (рекомендации для следующего этапа)

1. **WebUI** — форма партии с выбором приёмки (`PartLotType.php`, PATCHES.md п.2) не добавлена. Остатки в UI показываются без группировки по `id_acceptance`. Не блокирует API-работу.
2. **`report_hash` misnamed serialize**: `report_hash` в JSON не маппится на `$reportHash`. Шлюз работает (смотрит только `errors_count`), но хеш отчёта в БД пуст. Нужен `#[SerializedName('report_hash')]` на свойство или отправлять `reportHash`.
3. **permissions нормоконтролёра**: `@parts.edit` выдано admin'у, раздельное право «выпускать» рекомендовано, но не создано (см. README_УСТАНОВКА п.5).
4. **defaultParameterVisibility**: не включена через UI — поля ЕСКД из parameters не отображаются в KiCad-API (напомню).
5. **schema:update --dump-sql** показывает косметические расхождения Doctrine (SERIAL→IDENTITY, JSON→JSONB, пара индексов) — это не ошибка, но при следующей миграции может всплыть.
6. **Restore-тест после миграции** не прогонялся — бэкап сделан перед миграцией, обратный restore не проводился.

## Итого

**Д-1/Д-2 на стенде работают.** 4 приёмочных сценария прошли (ПИ-1, ПИ-4, ПИ-6, ПИ-7). 4 точечных правки под v2.13.1 внесены в комплект (файлы в `/tmp/d12/php_d1/` пропатчены, миграция применена). Маркеры `// >>> КОМПОНЕНТ` во всех 3 местах ядра на месте — гигиена форка соблюдена.

### Команды для переразвёртывания с нуля

```bash
# 1. Бэкап (обязательно перед миграцией!)
cd /opt/component && ./scripts/backup.sh

# 2. composer dump-autoload (после копирования файлов)
docker compose exec partdb composer dump-autoload

# 3. Миграция
docker compose exec partdb php bin/console doctrine:migrations:migrate -n

# 4. Кэш
docker compose exec partdb php bin/console cache:clear

# 5. Проверка
docker compose exec partdb php bin/console doctrine:schema:validate
```
