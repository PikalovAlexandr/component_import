# Покрытие KiCad HTTP Library API ↔ Part-DB — таблица для п.6 чек-листа М0

> Зафиксировано по канонической спецификации KiCad HTTP Libraries (dev-docs.kicad.org,
> v2) и документации Part-DB EDA-integration (docs.part-db.de). Прямое зондирование
> живого Part-DB не проводилось: на стенде localhost:8080 работает Open WebUI,
> Part-DB не развёрнут (см. примечание ниже).

## Как работает KiCad HTTP Library (кратко)

KiCad опрашивает внешний HTTP-сервис (ERP/PDM/Part-DB) по фиксированному
протоколу. Сервис обязан отдать 3 уровня JSON:

| Эндпоинт (относительно корня из `.kicad_httplib`) | Что отдаёт |
|---|---|
| `GET /` (root) | метаданные: `{ "meta": { "version": 1.0 }, "name": ... }` |
| `GET /categories` (или `/categories.json`) | список категорий (папок) для дерева библиотек |
| `GET /parts/category/{id}` (или `/parts/category/{id}.json`) | список деталей категории |

Каждая деталь — объект с жёстким набором полей. KiCad берёт **только их**:

```json
{
  "name":          "K50-35-100В-10",     // показывается в дереве Add Symbol, ключ
  "description":   "...",
  "symbol":        "K50-35:K50-35-100В", // lib_id символа (из ДРУГОЙ библиотеки!)
  "footprint":     "K50-35:8X2.5",        // lib_id футпринта (из ДРУГОЙ библиотеки!)
  "reference":     "C",                    // Designator по умолчанию
  "value":         "К50-35-100В-10",       // номинал в схему
  "datasheet":     "https://...",
  "keywords":      "кап конденсатор",
  "exclude_from_bom":    false,
  "exclude_from_board":  false,
  "exclude_from_sim":    false,
  "custom_fields": { ... }                  // ← произвольные поля (см. ниже)
}
```

**Ключевой нюанс протокола (источник риска №1 из плана):**
HTTP-library **не содержит графики символа/футпринта**. В `symbol`/`footprint`
передаётся лишь *lib_id*, ссылающийся на символ/футпринт в **отдельной**
файловой/HTTP-библиотеке (например, в Gitea). Сама графика грузится оттуда.

## Таблица покрытия: «что отдаёт/не отдаёт» для системы КОМПОНЕНТ

| Элемент контракта (по `контракт_полей_eskd.csv`) | Отдаётся через HTTP-API? | Как |
|---|---|---|
| Графический символ (УГО) | ⚠️ НЕТ напрямую | только ссылка `symbol`=`lib:name`; графика — из Gitea-библиотеки |
| Футпринт | ⚠️ НЕТ напрямую | только ссылка `footprint`=`lib:name` |
| 3D-модель | ❌ НЕТ | протоколом не предусмотрено; подставляется в футпринте `model ...` |
| Reference / Value / Datasheet | ✅ ДА | нативные поля |
| Description / Keywords | ✅ ДА | нативные поля |
| Наименование (графа перечня) | ✅ ДА | `name` детали (= имя символа базового варианта) |
| Тип (класс + группа) | ⚠️ через custom_fields | `custom_fields.Тип` — Part-DB отдаёт свойства детали |
| Документ (ТУ) | ⚠️ через custom_fields | `custom_fields.Документ` |
| Примечание | ⚠️ через custom_fields | `custom_fields.Примечание` |
| Код ОКП / приёмка | ⚠️ через custom_fields | `custom_fields.Приёмка 5. Код ОКП` (до сущности PartAcceptance) |
| Высота / Масса | ⚠️ через custom_fields | `custom_fields.Высота`, `Масса` |
| **Второе УГО (ГОСТ/IEC) на одну деталь** | ❌ **НЕТ** | протокол = 1 деталь → 1 `symbol`. Два УГО — доработка этапа 2 (Д-3) |
| Статус ЖЦ (разрешён/запрещён/архив) | ⚠️ через exclude-флаги | `exclude_from_bom/board`; статусы — доп. поле + фильтр выдачи |
| Цена / наличие / поставщик | ❌ НЕТ | это складской контур Part-DB (этап 3), не HTTP-library |

## Уточнение доработки Д-3 (на основе таблицы)

**Д-3 = «двойное УГО в HTTP-library».** Подтверждено количественно:

1. **Протокол KiCad отдаёт ровно один `symbol` на деталь** → отдать одновременно
   и ГОСТ, и IEC на одну позицию **невозможно** стандартным путём.
2. **Решение, заложенное в план (этап 2):** два представления HTTP-library с
   одинаковым набором деталей, отличающихся только `symbol` (lib_id):
   - `K50-35-GOST` → символы из Gitea-репо `symbols` (роль ГОСТ)
   - `K50-35-IEC`  → символы из Gitea-репо `symbols` (роль IEC)
   Разработчик подключает одно из двух; переключение проекта — утилитой
   `component-project switch` (уже реализовано).
3. **Что требуется от PHP-стороны Part-DB (этап 2):**
   - поле «роль символа» (ГОСТ/IEC) у детали/символьной ссылки;
   - эндпоинт отдаёт `symbol` по роли из настроек/токена или из двух разных URL.
4. **Запасной вариант (риск №1 плана):** если штатный HTTP-library Part-DB не
   даст гибкости — собственный тонкий эндпоинт в Python-сервисе поверх той же БД.
   Протокол прост (3 GET + JSON), реализация оценивается в ~1 чн, покрывает и
   custom_fields, и оба УГО без правок ядра Part-DB.

**Вывод по п.6 М0:** главный технический риск оценён количественно — стандартный
KiCad HTTP-API покрывает базовые поля и custom_fields (значит контракт полей из
п.3 будет доведён до KiCad), но НЕ покрывает два УГО и 3D-модель напрямую.
Оба ограничения имеют рабочие пути (два представления / `model` в футпринте),
блокировки этапа 1 нет.

## Примечание о стенде

На `localhost:8080` в текущем окружении запущен **Open WebUI** (LLM-фронтенд,
сервер `uvicorn`), а не Part-DB. Эндпоинты `/kicad-api/*`, `/api/parts` отдают
HTML SPA (200), а не KiCad/Api-Platform JSON. Поэтому таблица выше собрана из
спецификаций. Для эмпирического подтверждения (рекомендуется до закрытия М0)
нужно развернуть Part-DB из комплекта этапа 0 (`docker compose up`) и повторить
пробы: `curl /kicad-api/v1/categories.json` должен вернуть JSON категорий.
