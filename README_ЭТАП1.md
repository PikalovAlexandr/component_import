# Этап 1 — мастер импорта и валидаторы (Python-сервис, v0.1)

Пакет `component_import`: конвейер «разбор → валидация (В-2…В-6, В-9) → группировка
в детали со слиянием приёмки → автоисправления с протоколом → запись исправленной
библиотеки (+3D-заглушки) → верификация → отчёт → выгрузка в Part-DB».

## Установка и запуск
```bash
pip install .            # или: pip install -e . для разработки
component-import <каталог_с_библиотекой> -o <результаты> \
    --field-map config/field_map_pcad.csv \
    --upload http://componenty.local:8080 --token <API-токен>   # или --dry-run
```
Результаты: исправленная библиотека (`<lib>.kicad_sym`, `<lib>.pretty/`, `<lib>.3dshapes/`),
`ОТЧЁТ_<lib>.md` (сводка по правилам, список manual-решений, протокол исправлений),
`partdb_payloads.json` при --dry-run.

## Уровни находок
- **error** — дефект, блокирует статус «разрешён»; часть исправляется автоматически (fixable).
- **manual** — требуется решение библиотекаря (неклассифицированные площадки, номера вне ряда 1..N,
  детали без базового варианта, футпринты-«сироты»).
- **warning** — на усмотрение.

## Тесты (= ПИ-1/ПИ-2 в CI)
```bash
python3 -m pytest tests/      # «золотой» набор — серия К50-35
```
Проверяется: 130 символов → 65 деталей; 65 пар приёмки с разными ОКП; точные количества
дефектов каждого класса; ноль ошибок В-3…В-6 после автоисправлений; 12 3D-заглушек.

## Конфигурация
- `config/field_map_pcad.csv` — маппинг полей (сверить с контрактом этапа 0!).
- `importer.DEFAULT_CONFIG` — суффиксы приёмки, зависящие от приёмки поля,
  правила «текст → статус ЖЦ», обязательные поля (вынести в yaml по мере роста).
- `rules.DEFAULT_CLASS_RULES` — правила на класс (C/R/L: passive, имя=номеру).

## Что остаётся на PHP-стороне этапа 1 (Part-DB)
1. Сущность **PartAcceptance** (код приёмки, наименование, код ОКП) + API;
   до неё клиент кладёт данные приёмки в `_custom_fields` payload'а.
2. Статусы ЖЦ с правилом «разрешён только после валидации» (флаг от этого сервиса).
3. Загрузка графики в Gitea и привязка коммитов к деталям.

# Этап 3 (Python-часть, v0.4.0) — импорт прайс-листов (З-9)

`pricing.py` + CLI `component-price`, конвертеры в `converters/` (образец —
demo_distributor.py, ~30 строк на нового поставщика).

```bash
component-price import прайс.csv --supplier Дистрибьютор \
    --converter converters/дистрибьютор.py --parts <библиотека> \
    --map-store mappings.json --offers offers.json
component-price confirm --supplier Дистрибьютор АРТ-123=K50-35-100В-10.5
component-price status offers.json --max-age 90     # код 1, если есть устаревшие
```
Сопоставление: память подтверждений -> авто по нормализованному наименованию
(латиница-двойники приводятся к кириллице, приёмка «5» матчится на своё
наименование и получает СВОЮ цену) -> список на подтверждение с кандидатами.
offers.json — накопитель актуальных предложений (новый прайс вытесняет старый
по дате); он же — вход калькулятора этапа 4 и, далее, выгрузки в PartAcceptance.
Тест test_stage3_pricing.py = сценарий ПИ-6 целиком.

# Этап 4 (v0.5.0) — калькулятор стоимости изделия (Р-10, З-8)

`costing.py` + CLI `component-cost`. Вход: .kicad_sch ИЛИ BOM.csv
(Деталь;Приёмка;Кол-во[;Обозначения]) + библиотека + offers.json этапа 3 +
опционально остатки склада (Деталь;Приёмка;Остаток).

```bash
component-cost calc проект.kicad_sch --parts <библиотека> --offers offers.json \
    --qty 100 --acceptance 5 --stock остатки.csv --attrition 3 -o калькуляции --name изделие
component-cost compare калькуляция_v1.json калькуляция_v2.json
```
Логика: потребность = кол-во × тираж × (1+техотход); покрытие складом;
заказ = max(к_закупке, MOQ); действует ценовой порог с максимальным
кол-во_от <= заказ; между поставщиками сравнивается стоимость заказа, а не цена
штуки; устаревшие цены (> max-age) не участвуют при наличии свежих, иначе
берутся с пометкой. Несопоставленные позиции — в отчёт (код возврата 1) —
это заявки библиотекарю. Каждая калькуляция — версия (JSON+CSV с меткой
времени), версии сравниваются compare. Тесты = сценарий ПИ-5 (тиражи 10/100,
порог цены, MOQ, склад, приёмка «5», несопоставленное, версии, вход из схемы).

# v0.6.1 — выгрузка по итогам стенда М0

- Контрактные поля (Тип, Документ, Примечание, Группа, Класс точности,
  Исключён из ПЭ, Масса, Высота) уходят в parameters детали (группа «ЕСКД») —

  до схемы и netlist без доработок PHP (закрытие п.3 М0 «на проводе»).
- Маппинг полей (включая составной) применяется и к payload'ам выгрузки,
  а не только к записываемой библиотеке.
- Выгрузка: root http://<сервер>:<порт>, запись через /api/... с Bearer-токеном;
  kicad-api — read-only для KiCad (см. README этапа 0, дополнение).

# v0.7.0 — подготовка боевой выгрузки

- **Идемпотентность**: `component-import --upload` проверяет существующие
  категории/детали по имени (GET /api/...) и пропускает их — повторный запуск
  не плодит дубли; итог «создано/пропущено» в выводе.

  «5» до Д-1 привязываются к той же детали (различаются артикулом поставщика).
- CLI-тесты (test_cli_smoke.py): контракт аргументов всех четырёх утилит;
  покрытие обвязок 0% -> 84–92%, total 72% -> 89%.

# v0.8.0 — массовый импорт (component-batch, веха М1)

```bash
component-batch plan <корень_с_библиотеками> --field-map ... --tu ...   # ранжирование
component-batch run  <корень> -o out --field-map ... [--tu ...] \
    [--only ИМЯ]... [--skip ИМЯ]... [--limit N] \
    [--upload http://сервер:порт --token ... | --dry-run]
```
Обнаружение: пара `<Имя>.kicad_sym` + `<Имя>.pretty/` = библиотека = категория
Part-DB. Порядок «от чистых к грязным» (неисправимых error на деталь). Сбой
одной библиотеки не останавливает поток и попадает в сводку. Результаты:
исправленные библиотеки, ОТЧЁТ_<lib>.md на каждую, СВОДКА.md + СВОДКА.csv.
Выгрузка идемпотентна (v0.7.0) — прерванный прогон можно перезапускать.
